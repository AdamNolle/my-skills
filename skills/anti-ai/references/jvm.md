# JVM libraries: boundary contracts, partial I/O, and lifecycle

Research checked: **2026-10-02 UTC**. Select only the project matching the target's execution model. The pinned historical source and tests were inspected; upstream suites were not executed. Dates identify commits, not necessarily release publication. Use current supported APIs and local project conventions; these snapshots are research baselines, not versions to deploy.

## Guava: Java API compatibility and precise boundary contracts

- **Why selected:** Widely reused library code makes compatibility cost and input contracts explicit, unlike a private application helper.
- **Pin:** v29.0, `2d655e59ee0af2a0cabf877d5f85ababf813ff8e`, 2020-04-13. [Commit](https://github.com/google/guava/commit/2d655e59ee0af2a0cabf877d5f85ababf813ff8e)
- **Inspected code:** [guava/src/com/google/common/base/Preconditions.java](https://github.com/google/guava/blob/2d655e59ee0af2a0cabf877d5f85ababf813ff8e/guava/src/com/google/common/base/Preconditions.java), `checkArgument`, `checkState`, `checkElementIndex`, `checkPositionIndex`. Element indexes exclude the upper bound; insertion positions include it. Multiple overloads can serve real call-site and runtime constraints.
- **Tests and policy:** [guava-tests/test/com/google/common/base/PreconditionsTest.java](https://github.com/google/guava/blob/2d655e59ee0af2a0cabf877d5f85ababf813ff8e/guava-tests/test/com/google/common/base/PreconditionsTest.java) covers negative indexes, bad sizes, reversed ranges, null messages and overload selection. [CONTRIBUTING.md](https://github.com/google/guava/blob/2d655e59ee0af2a0cabf877d5f85ababf813ff8e/CONTRIBUTING.md) requests tests for significant changes. [README.md](https://github.com/google/guava/blob/2d655e59ee0af2a0cabf877d5f85ababf813ff8e/README.md) distinguishes unstable `@Beta` APIs, stable binary compatibility including deprecated APIs, and serialized forms without a general stability promise.
- **Operational questions:** Which callers link to this signature? Is this an element or a position? Does a boundary failure have the intended exception type and useful context? Is an apparently obsolete overload retained for compatibility? Track source, binary and serialization compatibility separately.
- **Do not copy:** Do not add Guava just to wrap a trivial JDK operation, reproduce every overload in a small app, or equate preconditions with a security trust boundary. The README explicitly disclaims protection against malicious callers. Kotlin's own `require`/`check` conventions may fit better.
- **License and generation:** [Apache-2.0 license](https://github.com/google/guava/blob/2d655e59ee0af2a0cabf877d5f85ababf813ff8e/COPYING). This is a symbol-level sample; generation, platform variants and all repository content were not audited. Do not remove repetitive overloads on visual evidence alone.

## Netty: Java async state, reentrancy and buffer ownership

- **Why selected:** Its decoder has observable ownership and callback-order obligations; it demonstrates why repeated checks and small state machines sometimes earn their cost.
- **Pin:** netty-4.1.53.Final, `d4a0050ef33cab2542a80e11489a4977a63859f8`, 2020-10-13. [Commit](https://github.com/netty/netty/commit/d4a0050ef33cab2542a80e11489a4977a63859f8)
- **Inspected code:** [codec/src/main/java/io/netty/handler/codec/ByteToMessageDecoder.java](https://github.com/netty/netty/blob/d4a0050ef33cab2542a80e11489a4977a63859f8/codec/src/main/java/io/netty/handler/codec/ByteToMessageDecoder.java), `callDecode`, `decodeRemovalReentryProtection`, `handlerRemoved`, cumulators. Decoding checks progress and handler removal; removal during child decoding is deferred; incoming buffers are released through failure paths.
- **Tests and review:** [codec/src/test/java/io/netty/handler/codec/ByteToMessageDecoderTest.java](https://github.com/netty/netty/blob/d4a0050ef33cab2542a80e11489a4977a63859f8/codec/src/test/java/io/netty/handler/codec/ByteToMessageDecoderTest.java) includes `handlerRemovedWillNotReleaseBufferIfDecodeInProgress`, removal during decode, partial reads, read-only buffers and failures while cumulating. [CONTRIBUTING.md](https://github.com/netty/netty/blob/d4a0050ef33cab2542a80e11489a4977a63859f8/CONTRIBUTING.md) prefers a failing JUnit reproducer for bug reports.
- **Operational questions:** Can callbacks remove/reenter the handler? Does every loop consume input, produce valid progress or stop? Who owns each retained buffer after success and exception? Test partial input, close/removal during delivery and an allocator/write failure, not just one complete happy-path message.
- **Do not copy:** Netty's reference counting, event-loop confinement and pipeline semantics are domain contracts. Do not import manual reference counting into ordinary managed application code or collapse the decoder state machine before proving all callback transitions safe.
- **License and generation:** [Apache-2.0 license](https://github.com/netty/netty/blob/d4a0050ef33cab2542a80e11489a4977a63859f8/LICENSE.txt). Native/platform/build-generated portions were not evaluated; the selected Java decoder and behavioral tests are the evidence, not a whole-repository quality or authorship claim.

## JUnit: Java test-engine lifecycle and bounded extension abstractions

- **Why selected:** A mature test framework shows legitimate adapters, configuration precedence and the difference between asserting a helper and executing the real path under test.
- **Pin:** r5.7.0, `a3528756923b588a7ecded2237cb13190229b543`, 2020-09-13. [Commit](https://github.com/junit-team/junit5/commit/a3528756923b588a7ecded2237cb13190229b543)
- **Inspected code:** [junit-jupiter-engine/src/main/java/org/junit/jupiter/engine/extension/TimeoutExtension.java](https://github.com/junit-team/junit5/blob/a3528756923b588a7ecded2237cb13190229b543/junit-jupiter-engine/src/main/java/org/junit/jupiter/engine/extension/TimeoutExtension.java), `intercept`, `decorate`, `ExecutorResource.close`. Explicit timeout configuration takes precedence; lifecycle adapters share narrow behavior; the root context owns the executor and bounded shutdown reports failure rather than silently leaking it.
- **Tests and contribution evidence:** [junit-jupiter-engine/src/test/java/org/junit/jupiter/engine/extension/TimeoutExtensionTests.java](https://github.com/junit-team/junit5/blob/a3528756923b588a7ecded2237cb13190229b543/junit-jupiter-engine/src/test/java/org/junit/jupiter/engine/extension/TimeoutExtensionTests.java) executes the engine, selects test methods and inspects execution outcomes for enabled/disabled timeout modes and lifecycle cases. [CONTRIBUTING.md](https://github.com/junit-team/junit5/blob/a3528756923b588a7ecded2237cb13190229b543/CONTRIBUTING.md) distinguishes discovered `Tests` classes from fixture `TestCase` classes and provides formatting/testing conventions. [documentation/src/docs/asciidoc/user-guide/extensions.adoc](https://github.com/junit-team/junit5/blob/a3528756923b588a7ecded2237cb13190229b543/documentation/src/docs/asciidoc/user-guide/extensions.adoc) documents extension lifecycle/storage contracts.
- **Operational questions:** Does the regression execute the actual framework path and inspect its outcome? Were fixtures accidentally counted as tests, or tests excluded by naming/discovery? Does an extension have a precise lifecycle owner and cleanup contract? Preserve purposeful test doubles and adapters; verify they do not mock away the defect.
- **Do not copy:** Test-engine reflection and extension plumbing need not exist in a normal service. Timing thresholds from this historical suite are not portable performance guarantees; prefer controlled clocks/schedulers where the target supports them.
- **License and generation:** [EPL-2.0 license](https://github.com/junit-team/junit5/blob/a3528756923b588a7ecded2237cb13190229b543/LICENSE.md). This sample does not establish authorship of all fixtures, documentation output or build artifacts; inspect file-level notices before copying.

## Okio: Kotlin I/O contracts and purpose-built delegation

- **Why selected:** Compact Kotlin multiplatform I/O code distinguishes an abstraction with a concrete streaming contract from a wrapper that only adds indirection.
- **Pin:** parent-2.8.0, `cbbe2a3babf326867b7c224c2ab275adc4d04496`, 2020-08-18. [Commit](https://github.com/square/okio/commit/cbbe2a3babf326867b7c224c2ab275adc4d04496)
- **Inspected code:** [okio/src/commonMain/kotlin/okio/internal/RealBufferedSource.kt](https://github.com/square/okio/blob/cbbe2a3babf326867b7c224c2ab275adc4d04496/okio/src/commonMain/kotlin/okio/internal/RealBufferedSource.kt), `commonRead`, `commonRequest`, `commonReadFully`, `commonIndexOf`, `commonClose`; also [JVM adapter](https://github.com/square/okio/blob/cbbe2a3babf326867b7c224c2ab275adc4d04496/okio/src/jvmMain/kotlin/okio/RealBufferedSource.kt). Boundary/state checks, EOF, retained partial bytes, search limits and platform delegation have separate meanings.
- **Tests and contribution evidence:** [okio/src/commonTest/kotlin/okio/CommonRealBufferedSourceTest.kt](https://github.com/square/okio/blob/cbbe2a3babf326867b7c224c2ab275adc4d04496/okio/src/commonTest/kotlin/okio/CommonRealBufferedSourceTest.kt) tests bounded searching, existing buffered data, insufficient input, segment-at-a-time reads and operations after close; [okio/src/jvmTest/java/okio/RealBufferedSourceTest.java](https://github.com/square/okio/blob/cbbe2a3babf326867b7c224c2ab275adc4d04496/okio/src/jvmTest/java/okio/RealBufferedSourceTest.java) tests JVM behaviors. [CONTRIBUTING.md](https://github.com/square/okio/blob/cbbe2a3babf326867b7c224c2ab275adc4d04496/CONTRIBUTING.md) emphasizes a small/stable project, failing bug tests, existing conventions and `./gradlew clean check`.
- **Operational questions:** Does a wrapper guarantee buffering, limits, ownership or platform compatibility? Is EOF distinguishable from an empty successful result? Does a failed exact read preserve the contract for partial data? Are common behavior and platform integration both tested?
- **Do not copy:** Do not erase expect/actual or delegated compatibility layers as duplicate code. Internal buffers are not thread-safety primitives. This historical `commonClose` calls source close before clearing the buffer; do not cite it as proof that every cleanup step runs after a close failure. Infer only the demonstrated contract.
- **License and generation:** [Apache-2.0 license](https://github.com/square/okio/blob/cbbe2a3babf326867b7c224c2ab275adc4d04496/LICENSE.txt). Multiplatform variants are not automatically redundant or generated; generation provenance was not audited. Follow the target's Kotlin/compiler/platform versions rather than copying 2020 syntax or internals.
