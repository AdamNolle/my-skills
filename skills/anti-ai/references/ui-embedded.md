## RxJS: TypeScript teardown, failure aggregation and virtual-time testing

- **Why selected:** Callback-driven TypeScript has reentrancy and cancellation obligations that neither ordinary lexical cleanup nor a single promise automatically handles.
- **Pin:** 6.6.3, `a4bcb84bbcd59abc6c4e811b57a15124757db2f2`, 2020-09-06. [Commit](https://github.com/ReactiveX/rxjs/commit/a4bcb84bbcd59abc6c4e811b57a15124757db2f2)
- **Inspected code:** [src/internal/Subscription.ts](https://github.com/ReactiveX/rxjs/blob/a4bcb84bbcd59abc6c4e811b57a15124757db2f2/src/internal/Subscription.ts), `Subscription.unsubscribe`, `add`. Unsubscribe marks the object closed and detaches child/parent references before calling user teardown; it attempts remaining children even when one throws, then reports aggregated errors. Adding to a closed subscription triggers immediate teardown.
- **Tests and contribution evidence:** [spec/Subscription-spec.ts](https://github.com/ReactiveX/rxjs/blob/a4bcb84bbcd59abc6c4e811b57a15124757db2f2/spec/Subscription-spec.ts) checks idempotence, late addition and completing all teardowns when one fails. [CONTRIBUTING.md](https://github.com/ReactiveX/rxjs/blob/a4bcb84bbcd59abc6c4e811b57a15124757db2f2/CONTRIBUTING.md) requires async-operator cases including empty/never streams, errors, early disposal and throwing callbacks, recommends marble tests, and calls for comparative performance tests rather than minute single-run differences.
- **Operational questions:** Can cancellation run twice or reenter? If one cleanup fails, which resources still need release? Are late callbacks prevented from mutating closed state? Exercise ordering, errors, early disposal and no-emission paths with the target's deterministic scheduler facilities.
- **Do not copy:** Do not introduce RxJS solely to manage one callback or reproduce its historical `any` casts and parent bookkeeping in a simple component. Use current TypeScript types and local lifecycle facilities; subscription teardown is not interchangeable with every promise or AbortSignal contract.
- **License and generation:** [Apache-2.0 license](https://github.com/ReactiveX/rxjs/blob/a4bcb84bbcd59abc6c4e811b57a15124757db2f2/LICENSE.txt). CONTRIBUTING explicitly identifies generated documentation and a generated table of contents; preserve generator ownership instead of editing output as if it were primary source.

## Qt: UI lifetime, event loops and environment-sensitive tests

- **Why selected:** A mature UI framework exposes ownership, deferred destruction and thread affinity; a visually harmless cleanup can break callbacks and UI behavior.
- **Pin:** v5.15.2, `40143c189b7c1bf3c2058b77d00ea5c4e3be8b28`, 2020-11-06. [Commit](https://github.com/qt/qtbase/commit/40143c189b7c1bf3c2058b77d00ea5c4e3be8b28)
- **Inspected code:** [src/corelib/tools/qscopedpointer.h](https://github.com/qt/qtbase/blob/40143c189b7c1bf3c2058b77d00ea5c4e3be8b28/src/corelib/tools/qscopedpointer.h), `QScopedPointer.reset`, `take`, cleanup policies; [src/corelib/kernel/qobject.cpp](https://github.com/qt/qtbase/blob/40143c189b7c1bf3c2058b77d00ea5c4e3be8b28/src/corelib/kernel/qobject.cpp), QObject lifetime/thread-affinity documentation and `deleteLater`. Scoped ownership and event-loop-scheduled destruction solve different lifetime problems.
- **Tests and test guidance:** [tests/auto/corelib/tools/qscopedpointer/tst_qscopedpointer.cpp](https://github.com/qt/qtbase/blob/40143c189b7c1bf3c2058b77d00ea5c4e3be8b28/tests/auto/corelib/tools/qscopedpointer/tst_qscopedpointer.cpp) exercises reset, destruction, arrays and signatures. [tests/auto/corelib/kernel/qobject/tst_qobject.cpp](https://github.com/qt/qtbase/blob/40143c189b7c1bf3c2058b77d00ea5c4e3be8b28/tests/auto/corelib/kernel/qobject/tst_qobject.cpp) covers queued invocation/context destruction and `deleteLaterInAboutToBlockHandler`. [tests/README](https://github.com/qt/qtbase/blob/40143c189b7c1bf3c2058b77d00ea5c4e3be8b28/tests/README) documents active-display/focus/window-manager assumptions for its historical UI tests.
- **Operational questions:** Who owns the object and on which thread may it die? Can a queued callback outlive its receiver/context? Does the test run with a meaningful event loop and display/focus setup? Test observable lifecycle and event order, and label missing GUI-environment verification.
- **Do not copy:** QObject parent ownership, deferred deletion and ordinary C++ RAII are not interchangeable. Do not give one object conflicting owners or replace deferred deletion solely for shorter code. Historical test-desktop assumptions are evidence of environmental sensitivity, not present-day setup instructions.
- **License and generation:** Inspected QtCore files offer commercial/LGPL-3.0/GPL alternatives in their headers; documentation has separate terms. Check the exact file/module license. [moc build documentation](https://github.com/qt/qtbase/blob/40143c189b7c1bf3c2058b77d00ea5c4e3be8b28/src/corelib/doc/src/includes/qt_generate_moc.qdocinc) explicitly describes generated output: edit the authored declarations/generator inputs, not moc results. Third-party directories have their own notices.

## Blender: application data-structure invariants and build-integrated testing

- **Why selected:** A large interactive application complements library/kernel references. Its data-structure tests illustrate validating invariants in addition to expected output.
- **Pin:** v2.83, `211b6c29f771809a39a2b8155e8bb64489c7522c`, 2020-06-03. [Commit](https://github.com/blender/blender/commit/211b6c29f771809a39a2b8155e8bb64489c7522c)
- **Inspected code:** [source/blender/blenlib/intern/listbase.c](https://github.com/blender/blender/blob/211b6c29f771809a39a2b8155e8bb64489c7522c/source/blender/blenlib/intern/listbase.c), `BLI_movelisttolist`, `BLI_remlink`, `BLI_freelistN`; [source/blender/blenlib/BLI_listbase.h](https://github.com/blender/blender/blob/211b6c29f771809a39a2b8155e8bb64489c7522c/source/blender/blenlib/BLI_listbase.h). Transfer clears the source list; unlinking and freeing are distinct operations with distinct ownership consequences.
- **Tests and build evidence:** [tests/gtests/blenlib/BLI_listbase_test.cc](https://github.com/blender/blender/blob/211b6c29f771809a39a2b8155e8bb64489c7522c/tests/gtests/blenlib/BLI_listbase_test.cc) validates bidirectional links/endpoints, sorting results and sort stability. [tests/gtests/blenlib/CMakeLists.txt](https://github.com/blender/blender/blob/211b6c29f771809a39a2b8155e8bb64489c7522c/tests/gtests/blenlib/CMakeLists.txt) registers relevant source tests; [build_files/cmake/Modules/GTestTesting.cmake](https://github.com/blender/blender/blob/211b6c29f771809a39a2b8155e8bb64489c7522c/build_files/cmake/Modules/GTestTesting.cmake) gates builds through `WITH_GTESTS` and registers executables with CTest.
- **Operational questions:** After mutation, do ordering, identity, endpoint and ownership invariants all hold? Are move/unlink/free semantics distinguishable? Is the regression actually enabled by the configured build, registered and executed? Assert invariants around edge cases, not just a final happy-path value.
- **Do not copy:** Intrusive C lists and custom allocators fit Blender's constraints; they are not a default replacement for standard containers in Java/Kotlin/Python/TypeScript. Do not infer UI/accessibility quality from this low-level sample or claim it audits Blender's architecture.
- **License and generation:** Selected implementation is GPL-2.0-or-later; the selected test file states Apache-2.0. [historical Blender licensing notice](https://github.com/blender/blender/blob/211b6c29f771809a39a2b8155e8bb64489c7522c/doc/license/BL-license.txt) does not erase file-specific notices. The pinned tree contains vendored `extern/` libraries and generated gtest headers; not all repository code is authored by Blender maintainers. Keep vendored/generated code outside ordinary cleanup scope.

## FreeRTOS: embedded queue contracts and execution-context discipline

- **Why selected:** Embedded application code needs explicit ISR/task boundaries, data-copy semantics and scheduling obligations that desktop refactoring advice often misses.
- **Pin:** Kernel V10.3.1-kernel-only, `88e32327e975ddde97c390bc5b6c1f8e7d9d239e`, 2020-02-19. [Commit](https://github.com/FreeRTOS/FreeRTOS-Kernel/commit/88e32327e975ddde97c390bc5b6c1f8e7d9d239e) Companion demo/test snapshot: V10.3.1, `89e7bbe292afd3912d1f0b2402cc506878bad869`, 2020-02-19. [Commit](https://github.com/FreeRTOS/FreeRTOS/commit/89e7bbe292afd3912d1f0b2402cc506878bad869)
- **Inspected code and API documentation:** [queue.c](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/88e32327e975ddde97c390bc5b6c1f8e7d9d239e/queue.c), `xQueueGenericSend`, `xQueueGenericSendFromISR`; [include/queue.h](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/88e32327e975ddde97c390bc5b6c1f8e7d9d239e/include/queue.h) documents copied item sizes, blocking timeouts, task-only calls and ISR wake/yield handoff. [README.md](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/88e32327e975ddde97c390bc5b6c1f8e7d9d239e/README.md) separates portable kernel code from compiler/microcontroller ports and directs users to configured demos.
- **Behavioral test evidence:** [FreeRTOS/Demo/Common/Minimal/QueueOverwrite.c](https://github.com/FreeRTOS/FreeRTOS/blob/89e7bbe292afd3912d1f0b2402cc506878bad869/FreeRTOS/Demo/Common/Minimal/QueueOverwrite.c) exercises a length-one queue, overwrite/peek/count invariants and ISR/task paths; its progress counter advances only without observed failures. The companion [FreeRTOS/Demo/Common/Minimal/QueueSet.c](https://github.com/FreeRTOS/FreeRTOS/blob/89e7bbe292afd3912d1f0b2402cc506878bad869/FreeRTOS/Demo/Common/Minimal/QueueSet.c) contains queue-set stress/demo cases. These are inspected test/demo sources, not proof of a complete hardware test run or coverage certification.
- **Operational questions:** Which context invokes the API? Can it block there? Are copied item sizes and pointer lifetimes correct? Is the higher-priority-task wake flag propagated as the port requires? Validate the actual port, interrupt priorities, configuration, timeout behavior and on-target failure signals.
- **Do not copy:** Do not replace context-specific APIs with a generic wrapper that hides ISR restrictions. Do not transplant critical-section/interrupt masking into server applications or treat assertions as hostile-input validation. Port-dependent scheduler behavior requires target evidence.
- **License and generation:** [MIT license](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/88e32327e975ddde97c390bc5b6c1f8e7d9d239e/LICENSE) for selected kernel; demo file has an MIT notice. The tree includes third-party ports. Startup files, vendor configuration and generated hardware material need separate provenance and license checks; not every port was inspected.
